# Decisions

- 2026-11-21: Detector = small ONNX model via onnxruntime (listed at oss.qnx.com). Confirm with QNX table it counts as the open-source AI module.
- 2026-11-21: One camera for MVP; stereo / downward camera are stretch.
- 2026-11-21: Audio to earbuds is the ideal output; servo + LEDs are the MVP output. Route TBD (phone over Wi-Fi is the default unless QNX Bluetooth works quickly).
- 2026-11-21: No fallback project; no Entire; no GoDaddy domain.
- 2026-11-21: Board is QNX 8.0 on Pi 5, Python 3.14, gcc on board. GPIO = text writes to /dev/gpio/N (rpi_gpio); no /dev/pwm, so servo is software PWM in hw/actuate.py. Header I2C (GPIO2/3 = SDA1/SCL1) is /dev/i2c1 (group i2c); hw/i2cscan.c probes it.
- 2026-11-21: Proposed pin map (unverified until wired): LED blue GPIO17/22, red GPIO23, green GPIO24, servo signal GPIO18, IR GPIO27, accelerometer on pins 3/5 (3.3V pin 1, GND pin 6). Servo power from the bank, not the Pi 5V pin. Level 1 shows neither green nor red (spec only defines green=clear, red>=2).
- 2026-11-21: hw/actuate.py takes `Actuator(gpio=...)` (object with set_out(pin), write(pin, on)); default DevGpio writes /dev/gpio/N, hw/fake_gpio.py records writes for tests/demo (`python hw/demo_alerts.py --fake`).
- 2026-11-21: hw/ir_trigger.py (HandWave: rising edge + cooldown) and hw/fall.py (FallDetector: freefall <0.4g then impact >1.3g (MMA7660FC at 0x4C, +-1.5g) within 1s) take injected readers/samples; real GPIO27 read and I2C accelerometer read are not written yet (chip and QNX read path unverified).
- 2026-11-21: hw/io_main.py is the io process: listens on /tmp/iris.sock (`--socket`, `--fake`), one vision client at a time, parses `<level> <direction>` lines (asserts on bad format; `fall` not handled yet) into Actuator.alert; `hw/send_alert.py 2 left` sends one line for bench tests.
- 2026-11-21: Accelerometer reader = hw/accel.c (QNX devctl: SEND 0x07=0x01 then SENDRECV regs 0x00..0x02, retries while any byte has bit6 set) streaming raw counts as text lines; hw/accel.py decodes (6-bit signed, 21.33 counts/g) and `Accel.read()` returns (x,y,z) g for FallDetector. UNVERIFIED on board: DCMD_I2C_SENDRECV struct usage (build with `gcc -o accel accel.c`) and chip presence (not yet seen on /dev/i2c1).
- 2026-11-21: IR reader = hw/ir_read.py `IrReader().read()`: writes "in" to /dev/gpio/27, reads text "0"/"1" (parse crashes on anything else). UNVERIFIED on QNX: input-mode command, read format, and sensor polarity (`active_high` flag; flip it if the wave reads inverted).
- 2026-11-21: Board hostname `iris`; Wi-Fi via phone/laptop hotspot in boot/wpa_supplicant.conf (venue Wi-Fi doesn't work). SSH `qnxuser@iris.local`; Windows needs `-m hmac-sha2-256`.
- 2026-11-21: Webcam = Logitech C920 in a blue USB 3.0 port; sensor service uses /etc/config/sensor/sensor_rpi5.conf; camera is SENSOR_UNIT 5; live feed verified with `camera_mux -n 1 -u 5`.
- 2026-11-21: QNX camera access isn't supported from Python, so vision (capture/detect/decide) is one C++ process and io (actuate/speak) is Python; they talk over a UNIX socket at /tmp/iris.sock, one line per Alert ("2 left\n").
- 2026-11-21: onnxruntime 1.24.4 (onnxruntime-dev), python3-opencv 4.12 and numpy install on the Pi via `sudo apk add` from repo.oss.qnx.com 8.0.5. python3-onnxruntime 1.24.4-r0 is broken: it ships without onnxruntime_pybind11_state.so, so `import onnxruntime` fails.
- 2026-11-21: cv2.VideoCapture(0) does not open the C920 on QNX (opened False, "GStreamer: pipeline have not been created"); camera capture must use the C++ camera API.
- 2026-11-21: C++ builds on the board: `sudo apk add qnx-sf-base-dev qnx-screen-dev`, then `clang++ -std=c++17 grab_frame.cpp -o grab_frame -lcamapi`. grab_frame wrote /tmp/frame.ppm from sensor unit 5.
- 2026-11-21: C920 default stream under sensor_rpi5.conf = YCBYCR (YUYV) 640x480, stride 1280.
- 2026-11-21: onnxruntime C++ runs on the Pi (build: `clang++ -std=c++17 ort_smoke.cpp -o ort_smoke -lonnxruntime`). Tiny YOLOv2 (416x416, fp32, default session options) = ~256 ms/frame (~4 fps). "Schema error" spam at load is harmless.
- 2026-11-21: Tiny YOLOv2 threads on the Pi: 1 = ~436 ms, 2 = ~248 ms, 4 = ~245 ms. Use 2 intra-op threads (no gain past 2, leaves cores for capture/io). pidin reports Cortex-A76 at 1500 MHz (Pi 5 rated 2.4 GHz) - ask QNX table if the clock can be raised.
- 2026-11-21: DEIMv2-Femto (deimv2_femto.onnx + .onnx.data, inputs images[1,3,416,416] float + orig_target_sizes[1,2] int64; outputs labels/boxes/scores x300) = ~120 ms/frame (~8 fps) on the Pi with 2 threads, 2x faster than Tiny YOLOv2.
- 2026-11-21: Option B chosen: C++ `vision` does capture, DEIMv2 detect and decide, and sends Alert lines over /tmp/iris.sock; Python `io` only actuates and speaks. decide() is ported from PR #3 (level 3 = in path, close and y2 > 0.9; direction tie = "ahead").
- 2026-11-21: Full vision loop (capture -> DEIMv2 -> decide) runs on the Pi at ~126 ms/frame (~8 fps). Level 3 on every frame in the first run was the orig_target_sizes bug below.
- 2026-11-21: DEIMv2-Femto labels are COCO 0-79 class indices (0 person, 56 chair, 60 dining table, 62 tv), not 1-90 category ids.
- 2026-11-21: DEIMv2 orig_target_sizes must be [width, height] (boxes are scaled by w,h,w,h). PR #3 detect.py passes [h, w], which shrinks x by 0.75 and stretches y by 1.33 (made nearly everything "close").
- 2026-11-21: Score threshold stays 0.4 (VISION_SCORE env overrides). At 0.2 Femto only adds duplicate/junk boxes; it misses large close objects cut off by the frame at any threshold. Plan: ultrasonic sensor (read by io) for "something close ahead"; interfaces change TBD.
- 2026-11-21: decide() "ahead" = left/right occupancy within 0.05 of each other (team decision; exact-tie rule from PR #3 practically never fired).
- 2026-11-21: Ultrasonic = HC-SR04 (5 V). VCC to 5 V, shared GND, TRIG straight to a GPIO, ECHO through a 1k/2k divider (5 V -> 3.3 V) to a GPIO; never wire ECHO directly. Read by io (stream B). Avoid GPIO 2, 3, 17, 18, 22, 23, 24, 27 (hw pin map).
- 2026-11-21: Removed two earlier lines (PR #4) saying the pipeline stays in Python; they were based on `import cv2` succeeding, but `cv2.VideoCapture` cannot open the C920 (see the C++ vision decisions above).
- 2026-11-21: HC-SR04 verified on the Pi: TRIG GPIO25 (pin 22), ECHO GPIO16 (pin 36) via the 1k/2k divider, read from Python with QNX rpi_gpio (`sudo`, busy-wait timing as in QNX's HC-SR04 sample). Steady readings, closing speed sign correct. Script: hw/ultrasonic.py (port of the team's Arduino sketch: median of 3, closing speed over 7).
- 2026-11-21: On QNX, Ctrl-C does not stop hw/io_main.py while it waits on the socket (SIGINT lands on the servo thread; Python only acts in the main thread). Confirmed: exits once a line arrives. Stop with Ctrl-\ for now; fix (stream B): `signal.signal(signal.SIGINT, signal.SIG_DFL)` at the top of main.
- 2026-11-21: First end-to-end run on the board: C++ vision -> /tmp/iris.sock -> hw/io_main.py -> real LEDs (red at level >= 2, green on clear). Both run with sudo (GPIO needs root; root-owned socket). Servo not wired yet. Direction flips left/right frame to frame in cluttered scenes; needs debouncing before speech/servo.
- 2026-11-21: io_main blocks SIGINT while the servo thread starts (threads inherit the mask), so Ctrl-C reaches the main thread and raises KeyboardInterrupt; `finally: actuator.off()` stops the servo thread and writes off to every output pin (17, 22, 23, 24, 18). UNVERIFIED on the board (needs `signal.pthread_sigmask` on QNX Python). kill -9 and SIGTERM still skip cleanup; manual reset: `sudo sh -c 'for p in 17 22 23 24 18; do printf off > /dev/gpio/$p; done'`.
- 2026-11-21: ultrasonic.py stays on the rpi_gpio module (verified on the board, mirrors QNX's HC-SR04 sample); the rest of hw/ uses /dev/gpio text writes. Not measured whether /dev/gpio reads are fast enough to time the echo pulse, so not switched. Pins don't overlap (ultrasonic 25/16).
- 2026-11-21: Team decision: camera + ultrasonic are fused in io (hw/fuse.py), not in vision, so Alert stays `<level> <direction>` and Range lines (`range <cm> <closing>` / `range none`) share /tmp/iris.sock. io is multi-threaded: one thread per client, a lock-protected Fusion, SIGINT blocked in every non-main thread. Fusion rule and thresholds in hw/fuse.py are untested starting guesses (NEAR 60 / MID 120 / FAR 250 cm, TTC 1.5 s). Whether Alert should carry the camera label: undecided.
- 2026-11-21: vision capture was already threaded (camera callback thread keeps the newest frame; next() drops stale ones), so a second detect thread would add throughput, not lower latency; not done. Measured sources of end-to-end latency: detect ~120 ms; the servo waited out the rest of a tap cycle (up to 1.1 s at level 1) before noticing a level change, now sliced at 50 ms (REST_SLICE_S). `IRIS_TRACE=1 python io_main.py` prints a CLOCK_MONOTONIC timestamp per received line to compare with vision's debug output.
- 2026-11-21: hw/ultrasonic.cpp (C++, QNX rpi_gpio edge pulses via a QNX channel, as in QNX's own c/Ultrasonic.c) replaces busy-wait timing; it adds a timeout QNX's sample lacks, so a missed echo sends `range none`. UNVERIFIED: not compiled (no QNX toolchain on the laptop). Needs QNX's common/rpi_gpio on the board: `git clone https://github.com/qnx/Raspberry-Pi-Hardware-Component-Samples ~/qnx-rpi && make -C ~/qnx-rpi/common/rpi_gpio`, then `clang++ -std=c++17 -O2 ultrasonic.cpp -o ultrasonic -I$HOME/qnx-rpi/common/system/gpio -I$HOME/qnx-rpi/common/rpi_gpio/public -L$HOME/qnx-rpi/common/rpi_gpio/build/<config dir> -lrpi_gpio -lm` (check the build dir name). Risk: rpi_gpio.h may not compile as C++ under extern "C"; echo timestamps are taken when the pulse is handled, not at the hardware edge. hw/ultrasonic.py (verified) stays as the fallback and bench tool.
- 2026-11-21: vision debounces Alerts before sending (vision/debounce.*): rise 1 frame (instant), fall 3, direction change 2; VISION_DEBOUNCE=up,down,turn overrides. 2/5/3 cut flicker but felt too slow on the board; the flicker fix comes from slow fall, so warnings stay instant (a false detection can flash red ~0.4 s).
- 2026-11-21: Camera + ultrasonic "depth" (option C): vision sends the in-path box that drives the Alert as `box <label> <x1> <y1> <x2> <y2>` every frame (separate from the debounced Alert line, which sends only on change); io's hw/describe.py estimates real height = box height * cm / F_NORM and drops a label that disagrees with its expected height range, then words a phrase. Fusion stays in io (ultrasonic does not depend on vision). Decided over fusing in vision so the ultrasonic safety net survives a vision crash and thresholds stay editable in Python.
- 2026-11-21: UNCALIBRATED constants in hw/describe.py: F_NORM = 1.27 (C920 vertical field of view guess; calibrate with a known-height object at a known distance: F_NORM = box_h * cm / height_cm), BEAM_X = 0.40..0.60 (image strip the ultrasonic covers; calibrate by placing an object in the beam), expected-height table and SLACK 0.6..1.5 (guesses). Labels without a table entry become "obstacle" when a range is present.
- 2026-11-21: Known gaps in phrases: no hysteresis, so a range flickering between a value and "none" (soft or angled surface) re-says the sentence; no audio route yet (io prints phrases); a dead vision process is not detected, only stale boxes and ranges expire.
- 2026-11-21: VERIFIED on the Pi (box-fusion commit, copied to ~/iris-box): hw/io_main.py parses box/range lines and the fusion + phrases work; SIGINT now exits cleanly (KeyboardInterrupt in main); a range that stops arriving expires via the watchdog. Pi has `git` and `python3`; qnxuser SSH key on the dev laptop is ~/.ssh/iris_board; io and vision both need sudo (root-owned socket; a non-root client gets PermissionError).
- 2026-11-21: VERIFIED: hw/ultrasonic.cpp builds and runs on the Pi against the real rpi_gpio.h (extern "C" is fine; no -D needed). Build: `git clone --depth 1 https://github.com/qnx/Raspberry-Pi-Hardware-Component-Samples ~/qnx-rpi && make -C ~/qnx-rpi/common/rpi_gpio`, then `clang++ -std=c++17 -O2 ultrasonic.cpp -o ultrasonic -I$HOME/qnx-rpi/common/system/gpio -I$HOME/qnx-rpi/common/rpi_gpio/public -L$HOME/qnx-rpi/common/rpi_gpio/build/aarch64le-debug -lrpi_gpio -lm -lsocket` (-lsocket is required). It reads about 16 times a second (~61 ms apart) and exits cleanly on SIGINT.
- 2026-11-21: FOUND on the Pi: with a stationary object near 55 cm the reading wanders 50-62 cm and the closing speed jumps +-20..60 cm/s, so at the 60 cm NEAR threshold the sentence flips "Stop. obstacle 60 centimeters" / "obstacle 60 centimeters" several times a second. Needs hysteresis in hw/fuse.py (or a minimum hold time) before speech or servo; closing speed needs smoothing before the time-to-contact rule is trusted.
- 2026-11-21: Pi rebooted at 18:51 UTC (power dip?) and came back with the sensor framework running but only /dev/sensor/camera1 and camera2; the USB webcam (unit 5) was not registered, so vision failed with `camera_open failed: camera_error_t=2`. Vision itself builds on the Pi (`clang++ -std=c++17 -O2 main.cpp capture.cpp detect.cpp decide.cpp debounce.cpp -o vision -lcamapi -lonnxruntime -lsocket`, 12 s) and loads the model. - 2026-11-21: FOUND on the Pi: DEIMv2 returns boxes slightly outside the frame (box 0 -0.004 -0.000 0.995 0.993). io's parse_box asserted on it, the client thread died and vision lost its connection. Fixed at the source: vision/detect.cpp clips every coordinate to 0..1 and drops boxes with no area left; io still asserts (a box outside the frame is now a real bug).
- 2026-11-21: Flicker fixes in io (tested on the Pi and by replaying 392 recorded readings): "range none" keeps the last good range for RANGE_HOLD_S = 1.0 s instead of dropping straight to the camera's level (41% of readings were no-echo with a dark object in front); hysteresis HYSTERESIS = 1.15 in hw/fuse.py (stay in a level until 15% past its limit); closing speed only counts toward time-to-contact above TTC_MIN_CLOSING = 70 cm/s (a stationary object read +-60, one reading showed -221 cm/s when the object moved); sentences limited to one per SAY_MIN_GAP_S = 1.0 s unless the level goes up. Replay of 392 readings (10-99 cm, a moving object, 24 s): level changes 51 -> 28 with hysteresis alone; not zero because the object really crossed the thresholds. Option if still too jumpy: debounce level drops like vision does (drop only after 3 consecutive readings).
- 2026-11-21: Full pipeline on the Pi (vision + hw/ultrasonic + io, 25 s): 328 frames at a mean 99 ms (CPU now 2400 MHz, was 126 ms at 1500 MHz), 335 box lines, 392 range lines, no errors. Desk test only: the camera lay low on a desk, so a close object at the bottom of the frame reads as level 3 ("touching the bottom = imminent"); retune after the chest mount.
